# 容量压测里的几个概念：拐点、安全容量、"下限"

> 背景：读 [capacity-baseline-report.md](../capacity-baseline-report.md) 时需要先理解这些概念。
> 工具实现见 `perf/baseline/baseline.py`，测法见 [perf/baseline/README.md](../../perf/baseline/README.md)。

## 1. 拐点（knee）

压测时逐级增加并发（例如 50 → 100 → 200 → 400）。下一级出现以下**任一**情况，当前这一级就是拐点：

- P99 超过 SLO（本项目：核心接口 P99 < 100 ms）；
- 错误率超过 0.1%；
- QPS 比上一级增长不到 5%：再加并发吞吐也上不去，只会让排队变长，说明已经饱和（`--flat-gain`）。

**拐点 = 最后一个仍然达标的级别**，也就是系统刚好还能满足 SLO 的极限吞吐。

## 2. 安全容量

**安全容量 = 拐点 QPS × 60%–70%**（`perf/baseline/baseline.py:169`）

拐点是极限，日常流量不能贴着极限跑，要留 30%–40% 余量，用来扛：

- 突发流量（活动、热点）；
- GC 停顿、慢查询等抖动；
- 部分副本故障后，流量集中到剩下的副本上；
- 缓存失效时请求回源。

容量模型里的 `capacity.app_safe_qps`、扩容时按"每副本多少 QPS"估算副本数，用的都是**安全容量**，不是拐点。

例（i7 本机基线，单副本）：

| 场景 | 拐点 | 安全容量 |
| --- | --- | --- |
| 店铺详情 | 200 并发，25,438 QPS | 15.3k–17.8k |
| 混合场景 | 100 并发，14,977 QPS | 9.0k–10.5k |
| 秒杀 | 100 并发，17,361 QPS | 10.4k–12.2k |

## 3. "只能当这台机器的下限"是什么意思

本机基线里，压测程序和被测服务跑在同一台机器上，互相抢 CPU。

- **"下限"指的是**：如果压测程序跑在别的机器上，这台机器上的应用**至少**能跑到这些数字，真实上限更高，只是没测出来；
- **不代表**整机已经满载，也不代表"这台 CPU 的极限就是这些"；
- **不能用来推算云服务器的表现**：笔记本 CPU 单核频率高，但有大小核、会降频，和云上的 vCPU 不是一回事，换了机器可能更高也可能更低。

### 怎么判断是压测端先到顶，还是应用先到顶

对比**客户端测到的 P99** 和**服务端自己统计的 P99**（Prometheus 的 `http_server_requests_seconds`）：

| 现象 | 结论 |
| --- | --- |
| 客户端 P99 很高、服务端 P99 很低、QPS 不再增长 | **压测端先到顶**：延迟加在压测程序发请求、收响应的路上，应用还有余力 |
| 服务端 P99 也超过 SLO | **应用真的慢了**，这个拐点可信 |

i7 基线里，店铺详情和秒杀属于前一种（400 并发时客户端 P99 172 / 259 ms，服务端只有约 14 / 33 ms），
混合场景属于后一种（服务端 P99 约 116 ms）。

### 想测出真实上限

1. 最有效：把压测程序放到局域网里另一台机器上；
2. 退而求其次：拐点改用服务端 P99 判断，同时确认压测端还能把 QPS 推上去；
3. 调整 CPU 分配（WSL 配额、压测程序可用的核数）后看拐点是否跟着变；跟着变，说明测到的是资源分配的边界，不是应用的上限。

## 4. 不同机器上的结果不能横比

| 机器 | 情况 |
| --- | --- |
| i7-14700HX（20 核 / 28 线程，31.7 GB） | 报告里的本机基线，JMeter 跑在 Windows 宿主上 |
| i5-1340P（4 性能核 + 8 能效核 / 16 线程，15.7 GB，28 W） | 整机 CPU 在 50 并发时就到 88%–96%；内存装不下基线配置（WSL 20 GB + `-Xmx4g`）；用 wrk 在同一虚拟机内压测 |

i5 这类机器**适合做改动前后的对比**（同一台机器、同一压测工具、固定参数），**不适合测绝对容量**。
对比时插上电源、切到高性能模式，并关掉占资源的应用，以减少降频带来的波动。
